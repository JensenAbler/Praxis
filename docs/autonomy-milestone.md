## Deployed contracts and limits

1. New projects have durable owner-scoped registration, Node/Python/static starter source, isolated workspaces, and publication to `main`. Repository visibility defaults to private. Repository creation credentials stay in the protected provisioner; each published repository receives its own deploy key. Remote creation and publication preserve uncertain outcomes rather than blindly repeating effects.
2. Diagnosis and recovery expose bounded operational events, explicit health observations, deployment history, registered service restart, and rollback to an identified recorded revision. They preserve runtime data and distinguish observed process health from unverified Discord or provider behavior.
3. Dependency installation uses opt-in public npm/PyPI registry access inside the development sandbox; ordinary jobs remain offline by default. Deployment bundles bind npm modules to the tested package manifests and runtime. Python virtual environments persist for development, but Python dependency bundles are not yet supported for deployment.
4. Self-improvement edits, tests, and publishes application source, prepares an exact release outside live authority, and activates through an independently supervised updater. Protected release status and recovery remain available when the coding application is down. Authentication, Git/deployment authority, privileged helpers, the updater, and permission policy remain protected; changing these uses the owner maintenance path.

New application hosting is limited to stateless Node services, Python standard-library services, and static sites under the fixed Praxis HTTPS origin. Private registries, Git-based dependency downloads, browser operation, arbitrary production administration, and general persistent application data management are not supported.
