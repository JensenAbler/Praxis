# Four-part autonomy milestone

The owner requests new projects, production diagnosis/recovery, ordinary dependency changes, and Praxis self-improvement. This supersedes the earlier exclusion of these capabilities. Main remains the default publishing branch. New repositories default to private unless visibility is explicitly selected; the Praxis repository remains public.

## Starting evidence

The actual phone task "Praxis live shutdown v1" published podcast-discord commit `5f6a212646f6fbe95b99135a2f918f9edc54eb90` and deployed that exact commit. Read-only follow-up confirmed clean GitHub main/VPS revision agreement and an active managed process. Persisted commit, push and deployment receipts completed. Twelve shutdown tests and three journal tests passed; the registered baseline/final suite each reported 93 passed and the same two existing failures. Live recording finalization under a real shutdown signal was not established.

This is native-phone work corroborated by GitHub and server records, distinct from the automated client fixtures used to qualify tool releases.

## Contracts being implemented

1. New projects: durable project registration and useful starter source, isolated workspaces, main publication and explicit repository visibility. Repository creation credentials stay in the protected provisioner, never command environments. Remote creation must remain recoverable after a lost response.
2. Diagnosis and recovery: bounded operational logs, explicit application-health observations, deployment history, registered service recovery, and rollback to an identified recorded revision. Preserve runtime data and record uncertainty rather than assuming a lost restart response means failure.
3. Dependencies: opt-in registry access through a protected network boundary; offline remains the default. Installation runs inside the development sandbox. Source/lockfile and dependency artifacts remain tied to the revision being tested and deployed.
4. Self-improvement: edit/test/publish Praxis application source, prepare an exact release, stage outside live authority, activate through an independent supervised updater, and recover/roll back from a fresh conversation. The authentication gateway, Git/deployment authority, updater and permission policy remain independently installed protected components.

## Qualification

Run the project test suite and authenticated MCP checks before activation. Exercise real sandbox registry access, new-project lifecycle, failed/duplicate/recovered operations, deployment recovery fixtures, and candidate rejection/restoration. Preserve production revisions during destructive failure fixtures. Native phone acceptance follows deployed tool discovery; API-client fixtures do not count as a phone run.

Implementation and acceptance evidence are in progress. No new capability is claimed deployed by this planning document.
